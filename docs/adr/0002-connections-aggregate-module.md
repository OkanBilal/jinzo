# Consolidate connections + connectionStates + connectionCredentials into one connections module

The three tables `connections`, `connection_tokens`, `connection_states` were originally owned by three sibling modules under the project's per-table 6-file layout. They were already entangled: `connections.service` imported `decryptSecrets` from `connectionCredentials/connectionCredentials.utils`, and `sync/sync.connection-utils.ts` had grown a duplicate `getConnectionWithSecrets` that read `connections` + `connectionTokens` directly and called `decryptSecrets` itself — bypassing the connections module entirely. The IPC namespace was already partially consolidated (`connections:saveCredentials` and `connections:checkCredentials` were registered on the `connections:*` namespace despite living in `connectionCredentials/connectionCredentials.ipc.ts`), and `connectionStates.service` was a 46-line pass-through over two repo methods. Applying the deletion test: removing the two satellite modules concentrated almost no logic anywhere — `connectionStates`'s entire surface fell into a few methods on `connections.service`, and the crypto helpers (`encryptSecrets`, `decryptSecrets`, `createTokenHash`, `parseProviderCredentials`, `parseConnectionMetadata`) became an internal seam of the deepened module.

We consolidated them into a single `connections/` module with the flat 6-file layout (one `connections.repo.ts` covering all three tables, one `connections.service.ts` covering identity, credentials, state, and provider resource-discovery, one `connections.utils.ts` for the crypto + provider-secret parsing kept private to the module). All IPC channels live under one namespace: the existing `connections:*` channels are preserved, and the two state channels move under it (`connectionStates:getAll` → `connections:listStates`; `connectionStates:updateById` → `connections:updateState`). The preload collapses from three sections (`connections`, `connectionStates`, `connectionCredentials`) to one (`window.api.connections`), and the renderer has one `connectionsApi.ts` with split RTK Query tag types (`Connection`, `ConnectionState`) so the Settings UI still refreshes sections independently. Cross-module readers (`sync`, `guards`) now import a single named function — `getConnectionWithSecrets` — from the module's barrel rather than reaching into utils, and the duplicate helpers in `sync/sync.connection-utils.ts` are removed (the file keeps only its non-connection utilities and the `connectionResources` read used by sync). The `connection_resources` table is deliberately left out of the aggregate; it is read by `workspaceResources.repo` directly, the same shape as `stats` joining `workspace_diffs` in ADR-0001.

The decision is hard to reverse (touches the IPC seam, preload surface, renderer api files, ~6 test files, and a cross-module duplicate in `sync`) and surprising without this context — a future reader sees one folder owning three tables, which violates the otherwise-uniform per-table convention. It's a deliberate exception for the same reason as ADR-0001: the three tables are one aggregate, the seam between them was already leaking (one cross-import in production code and one full duplicate in `sync`), and the layering symmetry was costing more in navigation than it earned in consistency. Future architecture reviews should not propose re-splitting them.
